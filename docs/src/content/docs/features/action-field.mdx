Run a server-side handler from a button. The in-flight form values are sent along, so the handler can read sibling fields. Config is **pure data** — no PHP callables — and handlers wire in via `add_filter` anywhere in your plugin.

```php
[
    'id'    => 'recalculate',
    'type'  => 'action',
    'label' => __('Totals', 'my-plugin'),
    'args'  => [
        'button_label' => __('Recalculate', 'my-plugin'),
        'variant'      => 'primary',
        'confirm'      => __('Rebuild every order total?', 'my-plugin'),
    ],
],
```

```php
add_filter(
    'my-plugin/action/default/recalculate/run',
    function ($unhandled, array $values, $request) {
        return ['status' => 'success', 'message' => __('Done.', 'my-plugin')];
    },
    10,
    3
);
```

## Single button or button group

<Tabs>
    <TabItem label="Sugar (single button)">
        Omit `args.buttons[]`. The button id defaults to the literal string `run`, so the filter is `{prefix}/action/{pageId}/{fieldId}/run`. Label and variant come from `args.button_label` / `args.variant`.

        ```php
        [
            'id'    => 'recalculate',
            'type'  => 'action',
            'label' => __('Totals', 'my-plugin'),
            'args'  => [
                'button_label' => __('Recalculate', 'my-plugin'),
                'variant'      => 'primary',
            ],
        ],
        ```

        Filter: `my-plugin/action/{pageId}/recalculate/run`
    </TabItem>
    <TabItem label="Button group">
        Declare an `args.buttons[]` array. Each button has its own id, label, variant, and confirm. Each posts to its own route and fires its own filter.

        ```php
        [
            'id'    => 'billing_tools',
            'type'  => 'action',
            'label' => __('Billing tools', 'my-plugin'),
            'args'  => [
                'buttons' => [
                    ['id' => 'refresh_stats', 'label' => __('Refresh stats', 'my-plugin'), 'variant' => 'primary'],
                    ['id' => 'export_csv',    'label' => __('Export CSV',    'my-plugin')],
                    ['id' => 'wipe',          'label' => __('Wipe',          'my-plugin'),
                     'destructive' => true,
                     'confirm'     => __('Wipe everything? This cannot be undone.', 'my-plugin')],
                ],
            ],
        ],
        ```

        Filters:

        - `my-plugin/action/{pageId}/billing_tools/refresh_stats`
        - `my-plugin/action/{pageId}/billing_tools/export_csv`
        - `my-plugin/action/{pageId}/billing_tools/wipe`
    </TabItem>

## Response shape

Return any of:

| Return                              | Effect                                                                                                                          |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `array{status, message?, html?}`    | `status` ∈ `success` / `error` / `warning` / `info`. `message` drives the snackbar. `html` renders an inline result panel.        |
| `WP_Error`                          | REST error — surfaces in the client error snackbar.                                                                              |
| `bool`                              | `true` → generic success, `false` → generic error.                                                                                |

The handler's return drives both UIs at once:

- **Snackbar** (`core/notices`) — always shown when `status` + `message` are set. Brief, dismissible.
- **Inline panel** — shown only when `html` is non-empty. Persistent, good for rich detail.

Short responses get just the snackbar; rich responses get both. No extra config switch — the dev picks the experience by what they return.

### Per-button result slots

Each button in a group owns its own inline panel. Clicking sibling buttons never wipes a panel they didn't produce — only that button's own subsequent clicks update or clear its slot. Network errors leave every panel alone.

## Confirm modal

Set `confirm` to require a modal step before the button fires. Two shapes:

```php
// Shorthand — just the message; title and labels use defaults.
'confirm' => __('Reset to defaults?', 'my-plugin'),

// Full form — override anything in one grouped key.
'confirm' => [
    'message'      => __('Regenerating immediately invalidates the existing key. Continue?', 'my-plugin'),
    'title'        => __('Regenerate API key', 'my-plugin'),
    'button_label' => __('Yes, regenerate', 'my-plugin'),
    'cancel_label' => __('Keep current key', 'my-plugin'),
],
```

The shorthand is for the common case; the array form is for when you want to tune the dialog without adding more `confirm_*` keys at the field level.

## Hook naming

```
{prefix}/action/{pageId}/{fieldId}/{actionId}
```

In sugar mode (no `args.buttons[]`) the `{actionId}` is the literal string `run`.

The filter default is a private `Unhandled` sentinel — if no listener attaches, the route returns `404 wireframe_action_unhandled` so the user sees a clear error rather than a silent no-op.

## Security boundaries

- **Same auth as Save / Reset** — the route is gated by the page's `capability` (default `manage_options`) and a WP REST nonce.
- **Declared fields only** — unknown payload keys are dropped before sanitisation. Each declared value runs through its type's `sanitize()` (so a `number` is an `int`, a `url` has been through `esc_url_raw`, etc.).
- **Sanitisers enforce format, not semantics** — your handler must still authorise what's being asked for (e.g. "can this user modify *that* order?") and use `$wpdb->prepare()` for anything it interpolates into SQL.
- **Raw HTML output is on you** — any `html` you return is rendered as `<RawHTML>` on the client. Escape anything user-derived with `esc_html()`, `wp_kses_post()`, or build the HTML server-side from trusted strings.
- **No callable leakage** — no PHP callables live in the config, so no callable target names ever leak into the page source.

## Reading sibling values

Because the request carries the in-flight values, your handler can read other fields on the page without any extra plumbing:

```php
add_filter(
    'my-plugin/action/default/billing/recalculate',
    function ($unhandled, array $values, $request) {
        $userId = absint($values['target_user'] ?? 0);   // sibling 'select' field

        if ($userId === 0) {
            return [
                'status'  => 'error',
                'message' => __('Pick a user first.', 'my-plugin'),
            ];
        }

        // …
    },
    10,
    3
);
```

The values are **sanitised** but **not validated**. Your handler is responsible for treating them as untrusted input — `$wpdb->prepare()`, cap checks, etc.

<Aside type="tip">
Prefer **named functions** over anonymous closures when wiring handlers — they're greppable, replaceable via `remove_filter`, and show up cleanly in tools like Query Monitor. See the [Action handlers recipe](/recipes/action-handlers/) for the pattern.
</Aside>
